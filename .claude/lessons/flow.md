# Orchestrator-Lessons (flow) — newest-first

- **Gesicherten WIP-Worktree einer abgebrochenen Session VOR `board next` erkennen und die zugehörige Story bewusst wählen — auch wenn `board next` eine andere liefert.** Beim Resume eines existierenden Worktrees (`EnterWorktree` meldet „resumed as-is") zuerst `git status` + `git log HEAD..origin/main`: uncommittete Story-Arbeit + ein „Worktree gesichert"-Commit des Loop-Releasers heißen Wiederaufnahme. `board next` lieferte hier S-009 (gleiche Priority, kleinere ID), aber S-013 war ebenfalls READY und zu ~90% fertig — Neuwahl von S-009 hätte die WIP-Arbeit kontaminiert oder erneut auf Eis gelegt (weiter veraltend, Konfliktrisiko wächst je gelandeter Story). Ablauf, der funktionierte: WIP als temporären Commit sichern → `git rebase origin/main` (Konflikte: additive Union; bei Datei-Ende-Konflikten in Test-Suiten die Datei deterministisch aus base/main/wip neu zusammensetzen statt Marker-Gymnastik — gemeinsamer Anker + gemeinsames Summary-Suffix) → `git reset --soft origin/main` + unstage, damit der Claim-Commit SAUBER (nur Story-YAML) vor der WIP-Arbeit gepusht werden kann → regulärer Build-Loop ab coder („verifizieren + fertigstellen", dokumentierte Alt-Findings aus lessons/coder.md als FINDINGS mitgeben). Typisches Integrationsrisiko der Wiederaufnahme: Namenskollisionen mit inzwischen gelandeten Storys (hier: `main()` in watchlist_pass.sh vs. orchestrator.sh — beide werden im selben Test gesourct). Lief in 1 Iteration durch, alle Gates PASS. *[seen-in: research-app S-013 2026-07-27]*

- **Memory-notierte „Spec-Lücken" vor einem Blocked-Entscheid IMMER gegen die echten Specs verifizieren.** Das Projekt-Memory führte S-008 als „ra_swot_item-Lücke — an requirement klären"; tatsächlich war die Tabelle in data-model.md §2.3 vollständig spezifiziert (Felder, Enums, UNIQUE, Indizes) und nur bewusst aus M1 herausgehalten (Kommentar in lib/run.sh) — S-008 war genau die Story, die sie anlegt. Blindes Folgen des Memory-Hinweises hätte die Story fälschlich auf Blocked/SPEC-LÜCKE gesetzt. Vorgehen: bei Memory-Zweifeln zuerst Spec + Datenmodell + Code-Kommentare lesen (5 min), erst dann SPEC-LÜCKE-Pfad erwägen — Memory ist Orientierung, nie Wahrheit. Der Lauf ging danach glatt durch (1 Iteration, alle Gates PASS). *[seen-in: research-app S-008 2026-07-27]*

- **Lessons-Gegencheck nach jedem Agent-Handoff: `.claude/lessons/*.md`-Deltas landen bei Subagenten gern im HAUPTORDNER statt im Story-Worktree.** Der reviewer schrieb seine S-012-Lesson trotz hart vorgegebenem Worktree-cwd in `<hauptordner>/.claude/lessons/coder.md` — im Worktree war kein Diff, und ohne Gegencheck wäre das Delta nie mit der Landung gefahren (verletzt flow-lessons-landing AC3) und beim nächsten fremden reset im Hauptordner verloren. Vorgehen: nach reviewer/coder/tester-Handoff `git -C <hauptordner> status --porcelain -- .claude/lessons/` prüfen; Delta per `git diff | git apply` in den Worktree portieren, Hauptordner-Datei per `git checkout --` zurücksetzen (nur die eine Datei), DANN Story-Commit. Achtung dabei: das `git apply` muss im Worktree-cwd laufen, nicht im Hauptordner. *[seen-in: research-app S-012 2026-07-27]*

Recovery S-007 lief so in <3 min inkl. Metrik-Touchpoint. *[seen-in: research-app S-007 2026-07-27]*

- **board-ship.sh erst regulär versuchen — der CI-Watch-Hang tritt nicht immer auf.** S-004 lief komplett durch (Merge, „CI grün", Done-Flip, Push) ohne Timeout; die S-005-Recovery (Remote-State prüfen, mechanisch nachziehen) bleibt der Plan B NACH einem Timeout, kein Grund, den Ship präventiv zu umgehen. Zweitens: auch bei hart im Dispatch-Prompt genanntem Worktree-cwd kann ein coder anfangs in den Hauptordner schreiben (S-004, selbst bemerkt + bereinigt) — der `git status`-Gegencheck im Worktree nach dem coder-Handoff (erwartete neue/geänderte Dateien wirklich da?) gehört zum Orchestrator-Pflichtblick vor dem reviewer-Dispatch. *[seen-in: research-app S-004 2026-07-27]*

- **board-ship.sh hängt in Repos ohne push-getriggerte CI an der CI-Watch.** research-app hat nur Dependabot-/Schedule-Workflows — nach dem Merge-Push startet nie ein Run, `gh run watch` wartet endlos (Timeout nach 5 min, Exit 143). Der Merge-Push selbst war da längst durch. Vorgehen nach Ship-Timeout (flow/P3-Muster): Remote-State prüfen (`git merge-base --is-ancestor <code-sha> origin/main`), bei gelandetem Code nur die Restschritte mechanisch nachziehen (Done-Flip via `BOARD_WRITER=flow board set`, committen, pushen) — kein blinder Re-Run. Außerdem: `board-ship.sh` verlangt einen committeten Working-Tree (L6-Guard) — der Orchestrator committet den Story-Diff (Code+Tests+Lessons, `feat(S-###): …`) VOR dem Ship-Aufruf. *[seen-in: research-app S-005 + S-006 2026-07-27 — 2 von 3 Ships hingen; Muster bestätigt, Recovery lief bei S-006 in <2 min]*

- **Board-Read erst NACH Wechsel in einen frischen Worktree (origin/main).** `git fetch` aktualisiert nur die Remote-Refs — `board next`/`board show` lesen den Working-Tree des cwd. Ein `/flow`-Start im stale Hauptordner kann eine auf origin/main bereits `Done` gelandete Story erneut claimen und ihr Done überschreiben (der Claim-Push geht als Fast-Forward durch, weil der Worktree frisch von origin/main abzweigt). Reihenfolge: EnterWorktree (fresh von origin/main) → DORT `board next` → Claim. Recovery: Story-YAML per `git checkout <origin-sha> -- board/stories/<story>-*.yaml` zurücksetzen, committen, pushen. *[seen-in: research-app S-001 2026-07-27 — Done-Flip f78ae15 um 07:30Z, Re-Claim um 07:32Z aus stale Hauptordner-Read]*
